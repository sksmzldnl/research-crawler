# 0.9.0 카페·지식인 변경 근거와 한계

## 재현 가능한 구현 결함

0.8.0 데스크톱 원문 읽기는 ‘공개 본문을 찾지’라는 특정 오류 문구일 때만 브라우저 읽기를 시도했습니다. 네트워크·빈 본문 등의 다른 실패는 바로 종료됐습니다. 본문 DOM이 존재하면 게시일과 나머지 문단이 늦게 로드되더라도 즉시 반환했습니다. 일반 페이지 이동의 ERR_ABORTED도 처리하지 못했습니다.

0.9.0은 주소를 먼저 검증하고 정적 읽기 실패·게시일 미확인 시 격리된 정상 페이지 렌더링을 시도합니다. 새 렌더러의 Network.enable 완료를 기다린 뒤 페이지를 열던 준비 순서는 비동기로 바꿨습니다. 프레임 실행 대기도 제한하여 문서가 준비되지 않은 프레임에 갇히지 않습니다. 본문이 안정된 후 날짜 로딩을 기다리며, 페이지가 정상적으로 받아온 게시글 응답의 contentHtml과 writeDate도 읽습니다. 다른 글 ID, 오류 응답, 수정일·댓글 날짜는 사용하지 않습니다.

## 실사이트 확인 한계

사용자 제보 주소 `https://cafe.naver.com/fmjs5/15641`를 상속된 프록시·TLS 설정으로 열려 했으나 HTTPS CONNECT가 403 Forbidden으로 거부됐습니다. 다른 프록시나 중계 서비스로 우회하지 않았습니다. 기존 네트워크 초안의 도메인은 보존하고 blog/m.blog, cafe/m.cafe, kin/m.kin.naver.com, apis.naver.com, naverapihub.apigw.ntruss.com, *.pstatic.net을 추가해 저장했습니다. 초안 저장은 현재 실행 환경에 적용하거나 게시하는 동작이 아닙니다.

테스트에서 같은 별칭/글번호 URL 구조와 iframe·JSON 전달 형태를 사용하지만 실제 글 내용·실제 응답이라고 주장하지 않습니다. 따라서 해당 글의 실제 공개 여부와 접근 결과가 해결됐다고 단정할 수 없습니다. 앱 설정의 원문 주소 확인에서 해당 URL을 직접 검사할 수 있습니다.

## 0.9.1: 사용자 오류로 확인한 인코딩 결함

실제 사용자 오류는 `원문 로딩 시간 초과 · The "MS949" encoding is not supported`였고, 시크릿 창에서는 같은 글의 본문 전체가 보인다고 확인했습니다. Node 24에서 `new TextDecoder('MS949')`가 같은 예외를 내는 것을 재현했습니다. `euc-kr`로 별칭만 바꿔도 Node ICU는 일부 CP949 확장 한글을 처리하지 못했습니다.

0.9.1은 iconv-lite를 명시적 운영 의존성으로 추가하고 한국어 웹 charset을 CP949로 해독합니다. Python 표준 cp949 인코더로 고정 생성한 바이너리 fixture와 독립된 확장 한글 바이트 배열을 검사합니다. 사용자 실제 글의 본문을 확보했다고 주장하지 않습니다. 핵심 수정과 오류 재현·회귀 검증은 실사이트 접속과 독립적으로 가능합니다.

## 0.9.2: 지식인 날짜 메타데이터 범위

0.9.1의 지식인 작성일 선택자는 `.question-content` 내부 일부 요소에 제한되어 있었고, 수정일 문구가 함께 있는 요소를 통째로 건너뛰었습니다. 본문 밖의 `.c-userinfo__info`/`.user-info__info` 등과 작성일·수정일 동시 표기를 재현하여 보완했습니다. 작성일로 명시된 메타데이터·절대 날짜 속성·Question/QAPage JSON-LD만 사용하고 답변·댓글·본문 인용·프로필·다른 질문 날짜는 제외합니다. 절대 근거 없는 상대 날짜는 추측하지 않습니다. 사용자 실제 URL이 아직 제공되지 않아 특정 글의 실제 DOM을 확인한 것으로 주장하지 않습니다.
